# Starknet → Hiero verifier

`StarknetVerifier` is an `IClprVerifier` for Starknet. It authenticates the queue state of a Cairo
ClprService on Starknet from Ethereum's sync committee alone. No Starknet sequencer, proposer or relayer
is trusted.

```
Ethereum sync committee (BLS, 2/3)                       EthL1StateVerifier (shared, deployed)
  → L1 execution state_root
  → Starknet core contract (MPT)                          StarknetCoreProof
      StarknetState {globalRoot, blockNumber}, proxy implementation (code hash pinned),
      optional pinned slots (programHash, aggregatorProgramHash, configHash, verifier)
  → Starknet global state root                            StarknetStateProver (deployed)
      = Poseidon('STARKNET_STATE_V0', contractsTreeRoot, classesTreeRoot)
  → contract trie (Pedersen Patricia, height 251) → ClprService leaf
      = H(H(H(classHash, storageRoot), nonce), 0)     (classHash pinned by the anchor)
  → storage trie → the channel's queue felts (derived from channelId, never taken from the proof)
```

## Contracts

| Contract / library | Role | Runtime size |
|---|---|---|
| `StarknetVerifier` | `IClprVerifier`: bundle and config paths, key derivation, felt range checks | 15.3 KB |
| `StarknetStateProver` | contract-trie + storage-trie proofs under a global root; Pedersen, Poseidon | 16.1 KB |
| `StarkPedersenTableA` / `B` (`StarkTables.sol`) | data contracts: Pedersen comb tables (17,281 B each); code hashes pinned in the prover | 17.3 KB each |
| `EthL1StateVerifier` | the Ethereum light client, shared with the OP Stack verifiers | — |
| `StarknetCoreProof`, `StarknetPatricia`, `StarkPedersen`, `StarkPoseidon` | libraries | — |

Deployment: the two table contracts, then `StarknetStateProver(tableA, tableB)`, then
`StarknetVerifier(l1StateVerifier, prover, profile, layout)`. `StarkTables.sol` is generated by
`npm run starknet:tables` (script/starknet/genStarkTables.ts) from the five cairo-lang Pedersen points and
`sha256("Hades" ‖ i)`.

## Pedersen / Poseidon in Hedera gas

There is no STARK-curve precompile, so both hashes are EVM arithmetic. They fit:

| Operation | Gas |
|---|---|
| Pedersen, internal (tables in memory) | ~48k |
| Pedersen, one external call incl. table load | ~68k |
| Poseidon permutation (`hash_many` of 3 = 2 permutations) | ~33k (~88k external) |
| Real STRK proof: 23 contract + 41 storage nodes, 3 keys (`verifyStorage`) | 4.87M |

Pedersen uses a fixed-base comb: 8 teeth × 31 columns for the 248-bit parts (255 precomputed affine
points per base), 15-entry tables for the 4-bit parts, Jacobian coordinates, one modexp inversion, comb
digits from a bit-spread transpose. Two things mattered more than the algorithm: copying the tables to
memory once per call instead of `EXTCODECOPY` per point, and making `p` opaque to the optimizer (it was
rebuilding the constant with SHL/ADD at every use) and keeping the stack shallow (no spills to memory).
Together they took a hash from ~88k to ~48k.

If a deployment needs more headroom, the options, in order of effort:
1. Batch-affine Pedersen: hash all nodes of a proof in lockstep and share one inversion per step
   (Montgomery's trick); affine additions are ~6 mulmod against 11, so roughly −35%.
2. Bigger combs: a second table per base halves the 31 doublings (~−10%) at the cost of 4 table
   contracts.
3. Optimized Poseidon (constant folding in partial rounds, unrolled): ~−40% on a cost that only occurs
   once per bundle.
4. A SNARK of the Patricia paths (Groth16 over BN254, ~250–350k gas to verify, constant): removes
   Pedersen from the EVM entirely, but adds a prover to the relayer and a circuit to audit.

## Gas and calldata

Execution gas inside the EVM (forge), add 21,000 + calldata gas for a transaction. "Dense" synthetic
tries: the contract-trie path has a binary node at each of the top 24 levels (Starknet Sepolia has ~23)
and every queue key at each of the top 22 levels (a service with ~4M storage slots).

| Bundle | Pedersen hashes | Gas | Proof bytes |
|---|---|---|---|
| ACK-only (8 channel keys), 512/512, dense | 25 + 33 nodes + 5 | 4.68M | 9.2 KB |
| + last-message and manifest keys (12 keys), dense | 25 + 78 nodes + 8 | 7.79M | 13.6 KB |
| ACK-only + sync-committee rotation | | 9.06M | 76.1 KB |
| 12 keys + sync-committee rotation | | 12.22M | 80.5 KB |
| Live: `verifyStarknetState` (L1 light client with 25 real non-signers + core contract) | — | 2.55M (eth_estimateGas) | — |

All fit Hedera's 15M gas and 128 KB calldata; the worst case (rotation + message + manifest keys, ~13.4M
with ~1.1M of calldata gas) has ~1.6M headroom. A relayer can always split a rotation into its own bundle.

## Trust assumptions

- **Ethereum's sync committee** (2/3 of 512), as for every Ethereum-settled verifier here.
- **Starknet's validity proof**: SHARP/the STARK verifier only registers facts for valid Starknet OS
  runs, and the core contract only advances `globalRoot` against such a fact. No challenge period.
- **Starknet governance.** The core contract is a StarkWare proxy with **upgrade delay 0** on Sepolia
  and mainnet, and governance can change `programHash`, `aggregatorProgramHash` and `configHash` at any
  time. A malicious upgrade or program hash could post an arbitrary root. The profile can pin the
  implementation's code hash and any core slots; a pinned verifier then stops (reverts) after such a
  change instead of following it. That trades liveness for safety: every Starknet OS release changes the
  program hash, so a pinned deployment needs a new verifier per release. Pinning nothing trusts
  governance like the chain's own bridge does.
- **The Cairo ClprService** at the channel's service address, identified by class hash (anchor
  `codeHash` field; zero disables the pin). A class can be replaced with `replace_class_syscall`; the pin
  catches that.
- **Liveness and freshness**: what the core contract holds on L1 is 3–4 h behind the L2 head on Sepolia.
  Replay and ordering are the ClprService's job (running hashes, message ids), as for the other verifiers.

## Storage layout ("CLPR Starknet layout v0")

There is no Cairo ClprService yet, so the verifier takes the layout as constructor data (`Layout`) and
this is the default a Cairo port should use:

```cairo
#[storage]
struct Storage {
    clpr_channels: Map<u256, ChannelQueue>,            // channelId
    clpr_messages: Map<(u256, u64), MessageValue>,     // (channelId, messageId)
    clpr_endpoint_manifest_commitment: u256,           // keccak256(ClprEndpointManifest protobuf)
}
#[derive(starknet::Store)]
struct ChannelQueue {        // offsets
    status: u8,              // 0   ClprTypes.ChannelStatus
    next_message_id: u64,    // 1
    received_message_id: u64,// 2
    sent_running_hash: u256, // 3 (low), 4 (high)
    received_running_hash: u256, // 5, 6
    endpoint_manifest_version: u64, // 7
}
#[derive(starknet::Store)]
struct MessageValue { running_hash_after_processing: u256 } // 0, 1
```

Running hashes are bytes32 read as big-endian u256 (`high << 128 | low`). Every felt is range-checked
against its Cairo type before it is decoded.

## Bundle format

RLP `[lightClientProof, coreProof, starknetProof, lastMessageId, bundleContent (, manifestPreimage)]`:

- `coreProof`: `[coreAccountProof, coreStorageProof (globalRoot, blockNumber, implementation, pinned…), implAccountProof]`
- `starknetProof`: `abi.encode(contractsTreeRoot, classesTreeRoot, classHash, storageRoot, nonce, uint256[] contractNodes, uint256[] storageNodes)`,
  nodes as 3 words each (binary `[l, r, 0]`, edge `[child, path, length]`) — the `starknet_getStorageProof`
  node set, deduplicated, each node hashed once.
- `lastMessageId`: empty, or `nextMessageId − 1` (adds that message's running-hash keys, as the EVM
  verifiers' 6th slot does).

`verifyStarknetState(proof, anchor)` returns `(globalRoot, blockNumber)` for relayers: it tells them which
Starknet block to fetch the storage proof for.

## Relaying and live data

Public Starknet RPCs (Pathfinder/Juno) serve `starknet_getStorageProof` only for the last ~60 blocks,
while L1 is hours behind. A relayer therefore has to fetch the storage proof **when the L2 head passes the
block the core contract will post next**, keep it, and submit once L1 has posted it. The live tooling does
exactly that:

```
npm run starknet-live:stage     # keeps a proof of every block L1 will post (stride learned from LogStateUpdate)
npm run starknet-live:refresh   # waits for L1 to post a staged block, captures the beacon + L1 proofs
npm run test:e2e:starknet-live  # replays test/e2e/fixtures/starknet-sepolia-live/capture.json on anvil
```

## Family

The same contracts serve any chain that runs the Starknet OS and settles through a StarkWare core
contract on Ethereum with the same state commitment, given its core address and layout: Starknet mainnet
(core `0xc662c410C0ECf747543f5bA90660f6ABeBD9C8c4`, same proxy layout and `identify()` as Sepolia), and
Starknet-stack appchains that settle on Ethereum through the same core contract (to be checked per chain:
OS version, state commitment, core layout). Chains that settle on Starknet (L3s) need one more hop (their core contract's storage on
Starknet), which the prover already supports. Not covered: Starknet's older (pre-0.13) roots and
StarkEx (different state trees).

## Limits

- Pedersen dominates the cost (~48k per trie node): bundles scale with trie depth, ~4.7M at today's
  depths.
- Live tooling depends on a public RPC exposing `starknet_getStorageProof` (Cartridge, ~60-block window).
- Starknet's L1 cadence (hours on Sepolia) bounds latency.
